Personal Task Assistant Changelog

Version 0.12.0 - 2026-08-07

Reply to the bot = act on the task:
- Replying to any bot message that mentions a task («⏰ Напоминание: #267…»,
  «👀 Нужно ревью: #247…») now applies the reply to that task. The first
  word picks the action: close-words (закрыто/готово/сделано/done/closed…)
  set status done, rework-words (доработай/переделай/rework…) return it to
  in_progress, block-words (блок/заблокировано/block…) set blocked, and
  anything else is a comment that changes no status. In every case the full
  reply text is appended to the task description as a dated
  "— YYYY-MM-DD HH:MM (Telegram): …" note, and the adapter answers with a
  localized confirmation in the chat. Replies to non-bot messages and
  replies without a task number are untouched.
- Reply commands are command traffic like the inline buttons: they
  short-circuit before the ingest path and never touch the
  ingestion-decision ledger or source-health counters
  (docs/ADAPTER_CONTRACT.md updated). Like the buttons, a reply from an
  allowed chat is the human's decision — this remains the only way a task
  reaches done.
- Voice and video-note messages now get an honest localized "can't
  transcribe voice yet" answer instead of silently being recorded as
  ignored, until the speech-to-text channel lands.
- Added `GET /api/tasks/{id}` (404 for unknown ids) for read-modify-write
  flows like note appending; documented in docs/API.md.
- Added tests for reply parsing (bot-authored targets only), first-word
  action classification in Russian and English, note appending with and
  without a status change, unknown-task replies, and the voice stub
  bypassing the ledger (147 tests total).
- Bumped the app version from 0.11.3 to 0.12.0.

Version 0.11.2 - 2026-08-06

- Fixed reminders re-firing on every poll for tasks with one target in the
  past and another in the future (e.g. a past reminder_at plus a future
  due_at): `is_reminder_due` re-armed the moment a reminder was stamped,
  because a future target always compared newer than the last send. With a
  30-second watch loop this repeated the same Telegram reminder endlessly —
  caught live within an hour of the loop watching a real board. A target
  now counts for re-firing only once it has actually passed
  (last_sent < target <= now), so each target fires exactly once and a
  future due date still produces its own reminder when it arrives. Added
  regression tests for both behaviors.
- Bumped the app version from 0.11.1 to 0.11.2.

Version 0.10.0 - 2026-08-06

Local work runner — the agent leg with no API billing:
- Added `automation/claude_work.py`: the claim -> work -> finish-to-review
  loop can now run through a headless Claude Code CLI session (`claude -p`)
  on the user's existing subscription instead of the metered Anthropic API.
  No ANTHROPIC_API_KEY is involved; a one-time `claude /login` under the
  same user is the only prerequisite.
- The headless session is isolated in code, not by prompt: it receives ONLY
  the task-assistant MCP server (`--strict-mcp-config` ignores every other
  configured server), only that server's tools are approved
  (`--allowed-tools "mcp__task-assistant"` — unapproved tools are denied in
  print mode, so no shell, repo, or web), it runs in a throwaway empty
  working directory so no project context leaks in, and the session is cut
  off after `WORK_TIMEOUT` seconds (default 900). Tasks moved to review are
  detected by diffing board snapshots taken before and after the run, so
  even a timed-out session reports exactly what it finished.
- Added `automation/work_runner.py`, the backend selector shared by the
  daily ritual and the watch loop: `WORK_RUNNER=claude` (also
  `claude-code`/`local`) picks the headless CLI, `api` or unset keeps the
  0.6.0 Anthropic-API loop. Both backends return the same worked-task shape,
  so digests and watch logs render identically. `WORK_CLAUDE_BIN` pins the
  CLI path for launchd's minimal PATH; `WORK_MODEL` optionally overrides the
  model. The watch loop now pre-flights the selected backend and warns once
  with the exact missing piece instead of spamming every tick.

Worker-mode rails in the MCP server:
- The safety rails for unattended runs moved into the MCP server itself, so
  they hold for ANY agent driving the tools — API loop, headless Claude
  Code, or a future runner. With `TASK_MCP_WORKER_MODE=1`,
  `task_assistant_update_task` refuses status done and cancelled (closing a
  task stays the human's decision; the agent's terminal state is
  waiting_review via finish_task), and `task_assistant_claim_task` enforces
  `TASK_MCP_CLAIM_BUDGET`: once the process has handed out that many
  successful claims, further claims are refused with a stop instruction.
- Default (non-worker) behavior is unchanged for interactive MCP use; the
  local runner sets both variables automatically. The deterministic
  evaluation gate (evals/verify_answers.py --write-loop) passes against the
  updated server; the eval board was re-seeded afterwards.
- Added integration tests for the rails (done/cancelled refusal, claim
  budget, non-worker passthrough) plus offline tests for backend selection,
  the headless command's isolation flags, the worker-mode MCP config, board
  diffing, and watch-loop work gating (132 tests total).
- Synchronized README, automation/README.md, docs/MCP.md ("Worker mode"),
  docs/SELF_HOSTING.md (the Docker image has no Claude Code CLI — containers
  keep using the API loop), and the daily-task-ritual skill.
- Bumped the app version from 0.9.1 to 0.10.0.

Version 0.9.1 - 2026-08-06

- Fixed the automation entrypoints crashing on wizard-generated .env files:
  `daily_run.sh` (since 0.6.0) and `watch_run.sh` sourced .env as bash, so an
  unquoted value with a space — the setup wizard wrote
  `APP_NAME=Personal Task Assistant` — became a command invocation and killed
  the runner under `set -euo pipefail` (the watch loop then crash-looped
  under launchd KeepAlive). Caught during the first real installation of the
  automation stack; it never fired before because no wizard-generated .env
  had ever met the schedulers on the same machine.
- Added `automation/env.sh`, a safe loader that parses KEY=VALUE lines
  without executing anything: comments, blank lines, and non-assignment
  lines are skipped, one layer of surrounding quotes is stripped (matching
  python-dotenv), and CR is trimmed. Both entrypoints now use it.
- The setup wizard quotes values containing spaces (`APP_NAME`,
  `TASK_HISTORY_SHEET_TAB`) so its .env is shell-safe by construction;
  python-dotenv reads the quoted form identically.
- Added `tests/test_env_loader.py`: loader behavior on spaces, quotes,
  comments, CRLF, missing files, and a wizard-output equivalence check
  between the bash loader and python-dotenv (119 tests total).
- Bumped the app version from 0.9.0 to 0.9.1.

Version 0.9.0 - 2026-08-06

The assistant gets a voice — Telegram delivery:
- Added `automation/notify.py`, the single outbound Telegram module used by
  the automation layer (the core app still never holds third-party
  credentials or calls third-party services). Configured entirely by env:
  `TELEGRAM_BOT_TOKEN` plus `TELEGRAM_NOTIFY_CHAT_ID`; unset means every
  caller behaves exactly as before. Messages are chunked under Telegram's
  4096-character limit at line boundaries, send failures return false instead
  of raising so an outage can never break the ritual or the watch loop, and
  the bot token is redacted from all logged errors.
- The daily ritual now delivers the digest to your Telegram chat after
  writing the dated file, and `--no-notify` skips delivery for manual runs.
- Added a spoken digest: with `TELEGRAM_DIGEST_VOICE=1` the ritual renders a
  short natural-language script (`render_spoken` — counts plus the hottest
  items by title, no ids or urls) through macOS `say` + `afconvert` into an
  AAC voice note and sends it with the text. On systems without those
  binaries the voice step skips itself and the text digest still goes out.

Reflexes — the watch loop:
- Added `automation/watch.py`: an opt-in loop that polls the board every
  `WATCH_INTERVAL` seconds (default 30) and reacts to what the once-a-day
  ritual is too slow for. Due reminders are pushed to Telegram and
  `reminder_last_sent_at` is stamped only after successful delivery, so the
  tracker's existing debounce holds and a Telegram outage never silently
  swallows a reminder; without Telegram configured nothing is stamped.
- Tasks entering `waiting_review` are announced with inline ✅ Done /
  🔁 Rework / ✋ Block buttons; which announcements were already made is
  remembered in `automation/.watch_state.json`, and a task that leaves review
  and re-enters it is announced again.
- With `WATCH_WORK=1` (plus `ANTHROPIC_API_KEY`) the watch loop kicks the
  same agent work loop the ritual uses as soon as agent-ready backlog
  appears, capped by `WATCH_WORK_MAX_TASKS` per kick — a task assigned to
  the agent is picked up within one interval instead of at 15:00. All
  work-loop safety rails apply unchanged.
- The loop presumes a running tracker and tolerates outages of the tracker
  and Telegram alike: each tick logs and retries instead of crashing, so
  KeepAlive supervisors never thrash.
- Packaged the loop for real deployments: `automation/install.sh --watch`
  installs a launchd KeepAlive job (macOS, `com.taskassistant.watch.plist` +
  `watch_run.sh`) or a systemd user service (Linux), and docker-compose
  gained an opt-in `watch` service behind the `watch` profile
  (`docker compose --profile watch up -d`).

Review buttons in the polling adapter:
- The Telegram polling adapter — the bot's single `getUpdates` consumer —
  now also handles `callback_query` updates from the review-request buttons.
  A press from an allowed chat applies the human's decision over the normal
  API (`PATCH /api/tasks/{id}`): ✅ sets `done`, 🔁 returns the task to
  `in_progress`, ✋ sets `blocked`; the adapter answers the callback and
  edits the original message so the outcome is visible in the chat. Closing
  a task stays a human-only action — agents still cannot set `done`; the ✅
  button is the human's finger arriving through Telegram.
- Callback traffic is command traffic, not source content: it never touches
  the ingestion-decision ledger or source-health scan counters, is ignored
  from disallowed chats, reports unsupported callback data without touching
  the tracker, and surfaces tracker failures as a callback alert instead of
  editing the message. Documented in `docs/ADAPTER_CONTRACT.md` ("Out of
  scope: command traffic").

Housekeeping:
- The agent work loop's default model moved from the retired
  `claude-opus-4-8` to `claude-sonnet-5` (board meta-work does not need a
  bigger tier); `DAILY_RITUAL_MODEL` still overrides it everywhere,
  including docker-compose.
- Added offline test coverage: notify chunking/buttons/redaction, watch
  reminder-stamping and review-announcement invariants against a mock
  tracker transport, adapter callback handling (allowed/disallowed chats,
  unknown data, tracker failure), and the spoken digest + delivery hooks
  (116 tests total).
- Synchronized README, `automation/README.md`, `adapters/README.md`,
  `adapters/telegram.env.example`, `docs/SELF_HOSTING.md`,
  `docs/ADAPTER_CONTRACT.md`, and the daily-task-ritual skill with the new
  surface.
- Bumped the app version from 0.8.0 to 0.9.0.

Version 0.8.0 - 2026-07-10

Source health and proactive visibility:
- Added durable per-adapter source state in SQLite and Firestore, plus
  `POST /api/agent/sources/report`, `GET /api/sources`, and
  `GET /api/agent/sources`, so a healthy empty scan is distinguishable from
  degraded coverage, unavailable access, expired auth, misconfiguration,
  rate limiting, and connector failure.
- Source reports retain `last_success_at` across later failures, record the
  latest sanitized error and run counts, and accept only HTTP(S) `action_url`
  values for an explicit reconnect flow; the core app still stores no source
  credentials and never performs third-party auth on an adapter's behalf.
- Heartbeat ordering is concurrency-safe: future-skewed reports are rejected,
  older/equal reports cannot overwrite newer state, SQLite uses a conditional
  update, Firestore uses a transaction, and SQL timestamps are normalized to
  UTC before the browser computes staleness.
- Added a Source health panel to the web UI. It refreshes every minute, shows
  the last check and normalized scan counts, exposes a safe reconnect link,
  and marks nominally healthy reports older than 24 hours as stale instead of
  silently presenting old access as current.

Ingestion decision memory:
- Added a durable ingestion-decision ledger keyed by `source_id`, stable
  `source_item_id`, and `content_fingerprint`, with `created`, `duplicate`,
  `ignored`, `needs_review`, and retryable `failed` outcomes. Deleting or
  cancelling a task no longer has to erase the decision that keeps the same
  source item from returning as noise.
- Added `POST /api/agent/ingestion/check` for batch preflight and
  `POST /api/agent/ingestion/decisions` for idempotent decision upserts.
  Unchanged terminal decisions are suppressed, changed fingerprints are
  reconsidered, and `revisit_after` provides an explicit time-based retry.
- Added Alembic revision `0003` for `source_states` and
  `ingestion_decisions`, updated the legacy/create_all stamping heuristic,
  and implemented the same contract with deterministic document ids in
  Firestore without requiring composite queries or storing credentials.
- Batched preflight uses one SQL query or one Firestore `get_all` call instead
  of up to 500 sequential reads, and Firestore task `external_id` values now
  use transactional reservation documents so concurrent ingest stays
  idempotent like SQLite, including legacy-task compatibility.

Reference adapter contract:
- Upgraded `adapters/telegram_polling_adapter.py` into the full reference
  implementation: successful `getUpdates` calls act as real read heartbeats,
  auth/network/API failures are classified and sanitized, allowed messages
  are fingerprinted before parsing, non-actionable content is recorded as
  ignored, and created/duplicate outcomes are written after idempotent ingest.
- Telegram task ids now include a stable bot/source namespace and a
  content-derived child identity. Edits safely preserve unchanged lines,
  create new/changed lines, never auto-delete progressed work, and transient
  failures retry with backoff while honoring Telegram `retry_after`.
- Added `docs/ADAPTER_CONTRACT.md` with the reusable six-step adapter flow,
  source status semantics, decision lifecycle, retry rules, privacy boundary,
  and complete payload examples; synchronized README, API docs, adapter docs,
  and the placeholder Telegram environment file.
- Added migration, source-health, decision-ledger, auth, retry, fingerprint,
  suppression, Telegram outcome, and normalized health-report tests.
- Bumped the app version from 0.7.0 to 0.8.0.

Version 0.6.0 - 2026-07-07

Daily automation:
- Added `automation/` — a once-a-day ritual that checks the board and takes
  work forward without the human starting it, scheduled via launchd at 15:00
  local time. This is the "second worker shows up for its shift" layer on top
  of the queue and MCP tools built in 0.4.0-0.5.x.
- Two deliberately separated layers with the safety split enforced in code,
  not the prompt:
  * `daily_ritual.py` (deterministic, always runs, never mutates the board):
    health-checks the tracker, reads it over REST, classifies the board with a
    pure `build_situation` function, and writes a dated digest to
    `automation/logs/` ordered by what needs the human first — overdue,
    waiting-your-review, blocked, unassigned-to-triage, due-soon, then the
    agent queue. The human always gets a report even if the agent layer is off
    or fails.
  * `work_loop.py` (opt-in, only with DAILY_RITUAL_WORK=1 and an
    ANTHROPIC_API_KEY): gives a model ONLY the task_assistant_* MCP tools and
    the worker instructions, then it claims -> acts -> finishes tasks to
    waiting_review; what it did is folded back into the digest.
- Safety rails live in `work_loop._dispatch`, not just the prompt: the agent
  has no shell/repo/web access (only MCP tools), it is refused when it tries to
  set a task to `done` (only the human closes tasks; its terminal state is
  waiting_review), and `--max-tasks` caps claims per run so an unattended run
  cannot run away. These rails are unit-tested without any API key
  (`tests/test_work_loop.py`).
- `daily_run.sh` is the scheduler entrypoint: it reuses a running tracker or
  starts a temporary one for the duration and stops it after, loads config
  from `.env`, and logs each run. `install.sh` renders and loads the launchd
  job (run by the user on purpose, since it schedules an agent that acts on
  their behalf; never auto-loaded). `com.taskassistant.daily.plist` fires at
  15:00 local.
- Added `tests/test_daily_ritual.py` (board classification and digest
  rendering: bucketing, overdue-vs-due-soon, reminder-driven overdue, worked
  reporting) and `tests/test_work_loop.py` (the claim budget and the
  done-refusal, verified without an LLM), bringing the suite to 61 tests.
- Verified end to end against a served board: the digest renders every section
  correctly, and `daily_run.sh` starts a temporary tracker, produces the
  digest, and stops the tracker afterward.
- Added the `daily-task-ritual` skill playbook and `automation/README.md`;
  routed both from AGENTS.md and README.md.
- Bumped the app version from 0.5.2 to 0.6.0.

Version 0.5.1 - 2026-07-04

Agent evaluation process:
- Added `evals/` with a repeatable evaluation process for the MCP server,
  measuring whether an agent can operate the task board given ONLY the MCP
  tools (no code access, no docs) — the quality bar for an autonomous
  assistant, not just a tool wrapper.
- `evals/seed_eval_board.py` recreates a deterministic 16-task board with
  fixed June-2026 timestamps and all deadlines in the past, so every answer
  stays stable no matter when the evaluation runs; re-seeding always produces
  the identical board.
- `evals/evaluation.xml` holds 10 read-only questions built to the MCP
  evaluation guidelines: independent, non-destructive, stable, multi-step,
  not solvable by keyword search, each with a single string-comparable answer
  (titles, counts, dates, priorities, an origin, an external id, True/False).
- `evals/verify_answers.py` is the free ground-truth check: it connects to
  the real MCP server over stdio exactly like Claude Code would, solves all
  10 questions programmatically through read-only tools, compares against
  evaluation.xml, and with --write-loop also exercises the claim ->
  in_progress -> finish -> waiting_review cycle end to end.
- Vendored the Anthropic mcp-builder LLM evaluation harness
  (`evals/evaluation.py`, `evals/connections.py`, Apache 2.0) which gives
  Claude the questions plus only the MCP server and reports accuracy,
  tool-call traces, and the agent's feedback on the tools; documented the
  full process in `evals/README.md` and linked it from README.md.
- Verified live against a served eval board: all 10 answers matched through
  the real stdio client, and the write loop claimed and finished the
  top-ranked task correctly (10/10, claim/finish OK).
- Bumped the app version from 0.5.0 to 0.5.1.

Version 0.5.0 - 2026-07-04

MCP server:
- Added an MCP (Model Context Protocol) server at `adapters/task_assistant_mcp.py`
  that exposes the JSON API as tools over stdio, so Claude Code, Claude Desktop,
  and any other MCP client can operate the tracker without custom adapter code.
- Nine tools with validated inputs, per-tool read-only/destructive annotations,
  and markdown or JSON output: `task_assistant_get_queue`,
  `task_assistant_queue_summary`, `task_assistant_claim_task`,
  `task_assistant_finish_task`, `task_assistant_create_task`,
  `task_assistant_update_task`, `task_assistant_list_tasks`,
  `task_assistant_ingest_context`, and `task_assistant_due_reminders`.
- The tool set encodes the product workflow: `claim_task` atomically takes the
  top-ranked Codex backlog task, `finish_task` hands completed work back as

Version 0.4.0 - 2026-07-04

Agent coordination:
- Added `POST /api/agent/claim` so a connected agent can atomically take the
  top-ranked Codex backlog task. The claim is a conditional backlog ->
  in_progress transition (conditional UPDATE in SQLite, transaction in
  Firestore), so multiple parallel agents polling the same queue can never
  claim the same task twice; the loser simply receives the next candidate or
  404 when nothing is claimable.
- Added `GET /api/agent/queue/summary` as a cheap polling endpoint that returns
  only the queue metrics block without loading, sorting, or serializing the
  task list.
- Claim events are recorded in task history with the `claimed` action and the
  `agent_api` note, including the previous task state.

Idempotent ingest:
- Added an optional `external_id` field (unique, up to 200 characters) to the
  task model, API schemas, and both stores.
- `POST /api/ingest/context` and `POST /api/agent/ingest/context` now
  deduplicate by `external_id`: replayed batches return the existing tasks in
  a new `duplicates` response list instead of creating copies, so webhook
  retries and adapters with lost offset state are safe to re-run.
- Direct task creation (`POST /api/tasks`, `POST /api/agent/tasks`) returns
  `409 Conflict` when the `external_id` already exists; uniqueness is also
  enforced by a database-level unique index.
- The reference Telegram adapter now stamps every ingested task with
  `telegram:<chat_id>:<message_id>:<line_index>` so repeated polling of the
  same messages cannot create duplicate tasks.

Database migrations:
- Introduced Alembic schema migrations for the SQL-backed store (revision 0001
  reproduces the 0.3.x schema, revision 0002 adds `external_id`).
- Startup now runs `alembic upgrade head` instead of `create_all`, so future
  schema changes apply automatically to existing local databases.
- Databases created by older releases (no `alembic_version` table) are detected
  by column inspection and stamped at the matching revision before upgrading,
  covering both pre-0.4.0 databases and databases created via `create_all`.
- `run-local.command` now detects missing dependencies after a `git pull`
  (such as the new Alembic requirement) and installs them into the existing
  `.venv` before starting the server.

Performance:
- Firestore `list_tasks` now filters `done`/`cancelled` tasks server-side with
  a `status not-in` query, so agent polling no longer reads the completed
  backlog from Firestore on every request; this cuts document reads and cost
  as history accumulates.
- `GET /api/agent/queue` no longer fetches all tasks including done ones when
  `include_done` is false; the summary is computed from the same single
  active-task read.
- Google Sheets task-history writes moved off the request path into FastAPI
  BackgroundTasks, so create, update, delete, ingest, and claim respond without
  waiting for the Sheets API when history export is enabled.
- Smart-rank sorting and queue summaries now compute "now" once per request
  instead of once per comparison, making ranking consistent within a response.
- Added `limit`/`offset` pagination to `GET /api/tasks` (limit 1-500).

Security:
- Local development auto-login is now enforced in the app itself: it only
  activates for requests arriving from the loopback interface, so accidentally
  starting Local Mode on `0.0.0.0` no longer signs in remote visitors; they
  see the auth setup page instead.
- API key comparison uses constant-time `secrets.compare_digest` instead of
  string equality.
- The Docker image now runs as a non-root `appuser` and includes the migration
  files needed at startup.

Testing and tooling:

  queue summaries/sorting/filters, atomic claim behavior, context-ingest

- Added Ruff configuration in pyproject.toml and normalized import order across

- Replaced the deprecated FastAPI `on_event("startup")` hook with a lifespan
